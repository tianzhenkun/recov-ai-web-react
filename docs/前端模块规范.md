# 前端模块规范

## 1. 核心边界

前端保持一套源码、一份构建产物。以下维度互相独立，不做一一绑定：

- 产品编码 `productCode`
- 登录布局 `loginVariant`
- 租户模式 `SELECTABLE` / `FIXED`
- 页面与业务模块
- API、路由、菜单、权限
- 品牌资源与主题
- 前端构建产物

产品可以复用登录布局，登录布局也可以服务多个产品。Billing 是可复用业务能力，可以存在于所有产品的同一份 dist 中；实际展示和可用性由后端菜单、权限、许可证和接口共同控制。

## 2. 目录职责

```text
config/routes.ts        路由聚合
config/routes/
  public.ts             登录、异常、账户、全局承接路由
  admin.ts              公共平台管理路由
  recov.ts              Recov 路由
  sales.ts              Sales 路由
  billing.ts            Billing 租户侧与平台运营路由

src/
  app/
    access/              Umi 权限入口的真实实现
    auth/                登录、站点配置和认证服务
    menu/                后端菜单服务
    shell/               全局壳层服务和承接页面
    extensions/          模块级全局扩展注册点
  api/
    main.ts              唯一主 API
    runtimeConfig.ts     浏览器运行时配置解析
  modules/
    admin/               公共平台管理能力
    recov/               Recov 页面、组件、服务和全局扩展
    sales/               Sales 页面和服务
    billing/             Billing 租户侧、运营侧、组件、权限和服务
  login-layouts/         登录控制器、布局 catalog、注册表和布局实现
  site-profiles/         服务端站点配置的解析边界
  branding/              公共品牌基线和站点品牌解析
  shared/                跨模块稳定类型、字典、OSS、产品目录、租户和用户服务
  pages/                 Umi 路由薄入口及尚未迁移的公共页面
```

`modules/admin` 表示平台管理业务，不表示“管理员角色”。权限仍使用后端权限码判断。

## 3. 路由、菜单和权限

- 静态路由按模块维护在 `config/routes/*.ts`，由 `config/routes.ts` 聚合。
- `src/pages/recov`、`sales`、`billing`、`ruoyi` 只保留 Umi 薄入口；真实实现位于 `src/modules`。
- 菜单完全以 `GET /system/menu/getRouters` 返回为准，前端不补造 Sales 等业务子菜单。
- 已登录用户访问普通业务页面时，以 `/system/menu/getRouters` 返回的原始完整路由树作为白名单，包括 `hidden` 路由；不使用经过视觉过滤的侧边菜单做授权。
- `hideInMenu` 和后端 `activeMenu` 只控制展示与高亮，不授予路由权限；详情页必须由后端授权树显式返回，不根据父路径推断准入。
- 授权树加载失败时 fail-closed，页面不提前渲染；加载成功但路径不存在时显示 403。
- Umi `access` 只能进一步收紧敏感页面，不能绕过后端路由白名单。
- 页面按钮权限码和后端接口鉴权分别执行，后端是最终授权边界。

## 4. API 规则

当前所有业务请求统一使用 `src/api/main.ts`，由主 Gateway 承接；不按产品、管理员或业务类型预先创建 API 通道。正式 release 仍生成的 `adminApi` 只做运行时配置解析兼容，业务请求忽略它，不构成第二套业务 API。

当前仓库没有浏览器直连 API。Recov 智能外呼的统计、记录和分析，以及 `/sys/voice` 的音色与并发配置，都通过主 API 调用后端。

只有新 upstream 被证明无法由主 Gateway 承接时，才在明确的所有者模块下设计对应直连 API；不提前为产品或服务预建通道类型。重新引入直连能力必须同时完成：

1. 明确模块所有权、接口和错误契约；
2. 增加安全的同源运行时地址、本地 Proxy 和配置校验；
3. 明确认证、401、审计和敏感信息边界；
4. 同步正式 Web/Nginx、release manifest、preflight 和部署验证。

只改浏览器运行时配置不能视为正式部署能力已经完成。

## 5. 新增产品

如果新产品仅复用现有前端能力，前端不必新增目录或重新构建，只需由后端和部署侧配置产品目录、站点配置、菜单、权限、许可证及可信产品上下文。

如果新产品带来新的前端业务能力：

1. 新建 `src/modules/<product>/pages`、`services`，按需增加 `components`、`permissions`、`extensions`；
2. 新建 `config/routes/<product>.ts` 并在路由聚合文件注册；
3. 在 `src/pages` 增加必要的 Umi 薄入口；
4. 若存在全局扩展，在 `src/app/extensions` 注册；
5. 默认使用主 API；如果出现主 Gateway 无法承接的新 upstream，按上一节完整设计并落地后再新增 API；
6. 确保后端完整授权路由树显式返回新业务路径，并补充路由、服务、权限和构建测试。

不要因为新增产品自动新增登录布局、API 通道或独立构建产物。

## 6. 新增登录布局

1. 在 `src/login-layouts/<variant>/` 实现 `LoginLayoutProps`；
2. 在 `src/login-layouts/catalog.json` 声明布局编码和名称；
3. 在 `src/login-layouts/registry.ts` 注册懒加载组件；
4. 运行 catalog 与 registry 一致性测试；
5. 由服务端站点配置返回需要使用的 `loginVariant`。

布局只负责展示差异，验证码、租户选择、登录、Token、重定向和错误处理继续复用统一控制器。

## 7. 迁移规则

- 迁移实现时先移动到 `src/modules`，再保留旧 Umi 薄入口，避免一次性改变路由 component 契约。
- 旧 `src/services/ruoyi/*` 暂时作为兼容导出；新代码直接引用所属模块服务、`src/app`、`src/shared` 或 `src/api/main.ts`。
- 兼容层只用于分阶段迁移，不得继续增加新的业务实现。
- 每批迁移后执行测试、TypeScript、Biome、生产构建和 CodeGraph 同步。
