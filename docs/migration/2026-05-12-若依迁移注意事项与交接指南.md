# RuoYi Vue 迁移到 Ant Design Pro React 注意事项与交接指南

> **历史快照，非现行规范。** 本文保留 2026-05-12 当时的迁移约定，不应用于指导当前开发或部署。当前业务请求只有主 API，`adminApi` 仅做正式 release 配置解析兼容且业务忽略；普通业务页面以 `/system/menu/getRouters` 的原始完整树（包括 `hidden` 路由）作为白名单。现行规则以项目 README、[前端模块规范](../前端模块规范.md) 和 [部署说明](../部署说明.md) 为准。

更新时间：2026-05-12

适用范围：`recov-ai-antd-pro-poc`

面向对象：后续继续迁移 Vue 页面到 React 的同事。

## 1. 核心结论

本次迁移不是把 Vue 代码逐行翻译成 React，而是在不改后端的前提下，把旧 Vue 项目的后端契约、权限规则、菜单规则、租户规则和常用交互迁移到 Ant Design Pro。

后续迁移时优先遵守三件事：

1. 后端接口契约必须和 Vue 当前行为一致。
2. React 组件实现可以更现代，但不能改变请求路径、请求方法、参数格式和鉴权语义。
3. 公共能力必须复用现有封装，不要在单个页面里重新手写一套。

## 2. 已确认的基础契约

### 2.1 接口前缀

当前 React 已支持和 Vue 一致的两套接口前缀：

- 默认业务接口：`/dev-api`
- 管理服务接口：`/admin-api`

默认请求必须走 `/dev-api`，只有 Vue 中明确使用 `adminService` 的接口，React 才使用 `/admin-api`。

对应封装：

- 默认请求：`src/adapters/ruoyi/request.ts` 中的 `ruoyiRequest`
- 管理服务请求：`src/adapters/ruoyi/request.ts` 中的 `adminRequest`
- 默认下载：`src/adapters/ruoyi/download.ts` 中的 `ruoyiDownload`
- 管理服务下载：`src/adapters/ruoyi/download.ts` 中的 `adminDownload`

不要在业务页面里手写 `/dev-api` 或 `/admin-api` 前缀。业务 service 中只写后端真实路径，例如 `/system/user/list`。

### 2.2 请求头

所有 RuoYi 请求都必须保持：

- `Authorization: Bearer <token>`
- `clientid: <UMI_APP_CLIENT_ID>`
- `Content-Language: zh_CN`

这些已经由 `ruoyiRequest/adminRequest` 统一处理。页面层不要重复拼请求头。

### 2.3 GET 参数格式

RuoYi 后端时间范围查询使用嵌套参数格式：

```text
params[beginTime]=2026-05-03 00:00:00
params[endTime]=2026-06-01 23:59:59
```

不能传成 JSON 字符串，也不能传成 `params=%7B...%7D`。React 中统一使用：

- `src/adapters/ruoyi/params.ts`
- `normalizeRuoyiParams`
- `addRuoyiDateRange`

凡是 Vue 中用 `addDateRange` 的页面，React 迁移时优先用 `addRuoyiDateRange`。

### 2.4 响应格式

RuoYi 常见返回：

- 普通响应：`{ code, msg, data }`
- 分页响应：`{ code, msg, rows, total }`

`ruoyiRequest` 会统一处理错误码、登录过期和加密响应。页面层只关心成功数据。

## 3. 迁移思路和工作方法

### 3.1 第一性原理

迁移的本质不是“换框架”，而是把一个已经在线上工作的业务系统，迁到另一个前端技术栈里继续正确工作。

所以判断迁移质量的第一标准不是代码看起来像 React，而是：

1. 同一个用户在 Vue 和 React 中看到的数据是否一致。
2. 同一个操作提交给后端的数据是否一致。
3. 同一个权限在 Vue 和 React 中是否表现一致。
4. 同一个菜单 URL 刷新、跳转、回显是否一致。
5. 出错时是否能定位到真实契约差异，而不是靠临时硬编码绕过去。

### 3.2 推荐迁移节奏

建议采用“底座优先、低风险页面验证、再进入复杂业务”的节奏。

第一阶段：底座

- 登录
- 请求适配
- token/clientid/语言头/加密
- 动态菜单
- 权限按钮
- 字典
- 删除确认
- 表格操作列
- 时间范围参数
- 导出/上传/下载
- 动态租户

第二阶段：系统管理类页面

- 用户
- 角色
- 菜单
- 字典
- 部门
- 岗位
- 参数
- OSS
- 租户
- 租户套餐

第三阶段：低风险运维类页面

- 操作日志
- 登录日志
- 通知公告
- 在线用户
- 缓存监控

第四阶段：真实业务模块

- 数据智能解析
- 智能外呼
- 全域送达
- 法律文书
- 诉讼管理
- 结算/对账
- 后台业务配置

不要一开始就迁复杂业务模块。复杂业务页面会同时暴露接口、权限、字典、上传、下载、表单联动和业务规则问题，如果底座没稳，排查成本会很高。

### 3.3 什么时候可以一次迁多个页面

可以一次迁多个页面的前提：

- 页面属于同一类模式。
- 接口契约简单。
- 主要是列表、查询、删除、导出。
- 没有复杂表单联动。
- 没有跨页面缓存或上下文状态。
- Vue 逻辑已经充分看清楚。

适合成组迁移：

- 操作日志 + 登录日志
- 字典类型 + 字典数据
- 部门 + 岗位
- OSS 文件 + OSS 配置
- 租户 + 租户套餐

不建议一次迁多个的情况：

- 有复杂新增/编辑弹窗。
- 有树形权限、菜单权限、数据权限。
- 有上传、导入、下载、预览。
- 有动态租户影响。
- 有流程、审批、解析任务、轮询进度。
- Vue 中存在较多 watch、computed、store、路由参数联动。

这类页面应先迁一个，验证稳定后再复制模式迁第二个。

### 3.4 每个页面迁移前必须先读 Vue

不要只看接口名字猜功能。迁移前至少读四处：

1. Vue 页面：`src/views/**`
2. Vue API：`src/api/**`
3. Vue 字典和权限用法：`v-hasPermi`、`useDict`
4. Vue 路由和菜单返回：后端 `/system/menu/getRouters`

必须先回答这些问题：

- 列表接口是什么？
- 详情接口是什么？
- 新增、修改、删除、导出分别是什么？
- 请求方法是什么？
- 查询参数有没有 `params.beginTime/endTime`？
- 表单提交是否包含只读字段？
- 是否有加密请求？
- 是否有上传或下载？
- 是否有 adminService？
- 按钮权限字符是什么？
- 页面是否受动态租户影响？

这些问题没回答完，不要开始写 React 页面。

### 3.5 先做 service，再做页面

推荐顺序：

1. 在 `src/services/ruoyi/**` 补 service。
2. service 层对齐 Vue API。
3. 页面只调用 service。
4. 页面不直接拼 URL、不直接处理前缀、不直接写 axios/request。

这样后续排查时可以先确认 service 契约，再看页面交互。

### 3.6 先复用公共封装，再考虑新增封装

页面迁移时优先复用已有能力。

只有满足以下条件才新增公共封装：

- 至少两个以上页面需要。
- 能减少真实重复逻辑。
- 不会隐藏业务差异。
- 命名和职责足够清晰。

不要为了“抽象”而抽象。一个页面独有的业务规则留在页面内更清楚。

### 3.7 先保守还原，再体验优化

第一版迁移以 Vue 行为为准。不要在还没验证接口契约前做过多体验重设计。

可以直接优化的部分：

- 操作列溢出。
- 删除确认文案。
- loading 状态。
- 空态。
- 表格密度和列宽。
- 表单布局。

不应擅自改变的部分：

- 请求路径。
- 请求方法。
- payload 字段名。
- 权限字符。
- 菜单 URL。
- 动态租户规则。
- 业务默认值。
- 后端返回字段语义。

### 3.8 遇到问题时的排查顺序

出现异常时，按这个顺序排查：

1. Network 中实际请求 URL 是否和 Vue 一样。
2. 请求方法是否和 Vue 一样。
3. 请求头是否包含 token、clientid、Content-Language。
4. Query 参数是否和 Vue 一样，尤其是时间范围。
5. Request payload 是否和 Vue 一样。
6. 后端响应是否和 Vue 一样。
7. React 页面是否有缓存、未刷新、旧 state。
8. 公共封装是否误处理了特殊接口。

不要第一时间判断后端有问题。只有 Vue 同接口同参数也失败，才考虑后端问题。

### 3.9 验证方式

每个页面至少做三类验证：

- 静态验证：TypeScript 通过。
- 请求验证：Network 与 Vue 对齐。
- 功能验证：新增、修改、删除、查询、导出等主流程可用。

当前环境浏览器自动化不稳定，所以不能只依赖自动化截图。人工用浏览器验证仍然必要。

部署前才需要 build；本地开发阶段非必要不要 build。

### 3.10 商用项目的质量线

后续迁移要按商用项目标准处理，不要只满足“页面能打开”。

最低质量线：

- 没有控制台运行时报错。
- 没有明显 UI 溢出和遮挡。
- 没有硬编码假数据。
- 没有绕过权限。
- 没有重复实现请求封装。
- 没有把敏感配置提交进仓库。
- 删除、导出、上传等高风险操作有明确反馈。
- 动态租户切换后数据上下文正确。
- 页面刷新后仍能正常进入。

如果做不到这些，不应进入下一批页面。

## 5. 登录与租户注意事项

### 5.1 登录页

登录已经从 Ant Design Pro 模板接口改为 RuoYi 接口：

- 租户列表：`/auth/tenant/list`
- 验证码：`/auth/code`
- 登录：`/auth/login`
- 当前用户：`/system/user/getInfo`
- 退出：`/auth/logout`

注意：

- 密码栏不能默认填充密码。
- 登录失败后需要清空用户输入的密码。
- 验证码图片来自后端 base64，需要拼为 `data:image/png;base64,...`。
- 记住账号只记住账号，不记住密码。
- 租户选择是否展示由后端 `/auth/tenant/list` 返回的 `tenantEnabled` 控制。
- 验证码是否展示由 `/auth/code` 返回的 `captchaEnabled` 控制。

### 5.2 动态租户切换

Vue 的动态租户切换逻辑是：

```text
dynamicTenant(tenantId) -> 跳转首页 -> 关闭/刷新页面
```

React 已按这个语义对齐。重要注意点：

- 切换后不要立即调用 `getInfo`。
- 动态租户不是重新登录，也不是切换用户身份。
- 后续列表数据依赖后端当前动态租户上下文返回。
- 清除动态租户时调用 `/system/tenant/dynamic/clear`。
- 动态租户状态清理要覆盖退出登录场景。

如果切换后数据没有变化，先查：

1. `/system/tenant/dynamic/{tenantId}` 是否成功。
2. 后续列表请求是否带同一个 token 和 clientid。
3. 页面是否复用了旧缓存。
4. 是否错误地在切换后刷新了 `getInfo`。

## 6. 菜单与路由原则

后端菜单接口 `/system/menu/getRouters` 是菜单展示来源。React 只做转换，不重新定义业务菜单。

当前处理方式：

- 后端动态菜单转换为 Ant Design Pro 菜单。
- 已迁移页面在 `config/routes.ts` 中配置真实 React 页面。
- 未迁移页面走 `src/pages/ruoyi/placeholder` 占位页。
- Ant Design Pro 模板示例页面放入“模板示例”分组保留。

后续迁移页面时：

1. 先确认后端菜单返回的 `path` 和 `component`。
2. 在 `config/routes.ts` 添加对应真实页面路由。
3. 不要改后端菜单数据结构。
4. URL 应尽量保持和 Vue 一致，避免影响菜单高亮、收藏、刷新和后续权限定位。

## 7. 页面迁移流程

建议每个页面按以下顺序迁移：

1. 找 Vue 页面和 API
   - Vue 页面通常在 `src/views/**`
   - Vue API 通常在 `src/api/**`
   - 先看请求路径、请求方法、参数格式、导出/上传方式。

2. 补 React service
   - 放到 `src/services/ruoyi/**`
   - 默认用 `ruoyiRequest`
   - Vue 中使用 `adminService` 的接口才用 `adminRequest`
   - 导出用 `ruoyiDownload` 或 `adminDownload`

3. 补路由
   - 在 `config/routes.ts` 为已迁移页面挂真实组件
   - 保持 URL 与后端菜单一致

4. 实现页面
   - 列表优先用 `ProTable`
   - 表单优先用 `ModalForm`、`DrawerForm` 或现有页面已采用的 ProComponents 模式
   - 行操作统一用 `TableActions`
   - 权限按钮统一用 `PermissionButton`
   - 删除统一用 `useDeleteConfirm`
   - 时间范围统一用 `addRuoyiDateRange`

5. 对照 Vue 验证
   - 请求路径是否一致
   - 请求方法是否一致
   - 参数名是否一致
   - 日期范围是否一致
   - 新增/修改 payload 是否一致
   - 删除、导出、上传是否一致
   - 权限字符是否一致

6. 做最小必要验证
   - 本地开发阶段非必要不要 build
   - 至少跑 `npm run tsc -- --pretty false`
   - 部署前才 build
   - 浏览器自动化在当前环境不稳定，不要把它作为唯一验证方式

## 8. UI 与交互原则

### 8.1 删除确认

统一用 `Modal.confirm`，不要混用 `Popconfirm`。

删除文案建议包含：

- 删除对象类型
- 对象名称或编号
- 操作不可恢复

例如：

```text
确认删除“用户管理”菜单吗？
将删除菜单编号为 100 的数据，操作不可恢复。
```

### 8.2 表格行操作

已迁移页面曾出现操作列过宽、按钮溢出的问题。后续统一：

- 行操作使用 `TableActions`
- 高频操作前置
- 低频或危险操作收纳到“更多”
- 删除使用危险色
- 图标来自 Ant Design Icons，不手写 SVG
- 不要为了解决宽度问题随意删业务必要字段，先优化操作列布局

### 8.3 表单回显

字典、状态、默认值要以 Vue 现有语义为准。

已确认规则：

- 字典样式属性为空时，回显为“默认”。
- 状态类字段通常使用字符串值，例如 `"0"`、`"1"`。
- 新增和编辑表单 payload 要分别确认，不要把只读字段或当前用户不可编辑字段误提交。

### 8.4 业务页面风格

这是管理后台，不做营销页风格：

- 信息密度要足够。
- 表格、筛选、操作区要稳定。
- 不要加无意义装饰。
- 不要嵌套卡片。
- 操作按钮、状态、空态、loading 要完整。

## 9. 后端契约注意事项

后端不改是当前前提。遇到问题时先证明是不是前端契约不一致。

优先检查：

- URL 前缀是否正确。
- 是否误用了 `/api`、`/prod-api` 或硬编码完整后端地址。
- 请求方法是否和 Vue 一致。
- `Content-Type` 是否正确。
- GET 嵌套参数是否被序列化成 `params[key]`。
- `clientid` 是否存在。
- `Content-Language` 是否是 `zh_CN`。
- 加密接口是否设置 `isEncrypt: true`。
- 上传 `FormData` 是否删除了手写 `Content-Type`。
- 下载是否使用 form-urlencoded。

不要为了让页面临时可用而改成前端假数据或硬编码租户、菜单、权限。

- `/dev-api` 和 `/admin-api` 代理必须和 Vue 线上配置一致。
