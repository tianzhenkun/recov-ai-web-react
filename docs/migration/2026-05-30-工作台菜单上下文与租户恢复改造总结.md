# 2026-05-30 工作台菜单上下文与租户恢复改造总结

> **历史快照，非现行规范。** 本文保留 2026-05-30 当时的菜单与租户恢复实现，不应用于判断当前路由授权。当前普通业务页面以 `/system/menu/getRouters` 的原始完整树（包括 `hidden` 路由）作为白名单，授权加载失败时 fail-closed；`activeMenu` 和 `hideInMenu` 只影响展示。现行规则以项目 README、[前端模块规范](../前端模块规范.md) 和 [部署说明](../部署说明.md) 为准。

## 1. 业务背景

本轮改造对应的是若依前端迁移过程中的一组连续业务诉求，核心不是单点页面 bug，而是「菜单组织方式」与「运行时上下文恢复方式」的整体重构。

业务侧的真实目标有两条：

1. 菜单组织目标
   - 将 `账户管理`、`后台管理`、`系统管理` 这类目录型菜单从左侧默认菜单中抽离出来。
   - 这些目录不再直接出现在左侧默认导航中，而是挂到右上角头像下拉中，由用户按“工作台”方式切换。
   - 点击某个目录后，左侧只展示该目录下的子菜单。
   - 点击左上角 Logo 后，需要回到默认左侧菜单，而不是继续停留在某个目录工作台内。

2. 上下文恢复目标
   - 浏览器刷新后，左侧菜单必须能根据当前 URL 自动恢复，不能出现“右侧页面已经是目录内页面，但左侧菜单还停留在默认菜单”的错位。
   - 超级管理员切换租户后，菜单上下文也必须与当前路径重新对齐，不能因为菜单缓存或内存状态导致左右两侧不同步。
   - 首页 `/`、占位页“返回业务首页”等入口也必须统一走同一套上下文恢复逻辑，避免局部跳转继续使用旧逻辑。

这意味着本轮改造的业务本质不是“加一个下拉菜单”，而是：

- 把原来的“全量后端菜单树”拆成“默认菜单视图”和“工作台菜单视图”两种展示模式。
- 让菜单上下文不再依赖纯内存态，而是能从 `pathname + 菜单树` 反推恢复。

## 2. 设计原则

本轮实现遵守了以下工程原则：

1. 不做补丁式刷新
   - 放弃了用版本号或强刷参数强行触发 `ProLayout` 菜单重刷的做法。
   - 不再依赖“变更一次状态就赌框架会刷新”的方案。

2. 显式建模菜单模式
   - 将菜单状态抽象为：
     - `default`
     - `workspace`
   - 并用 `activeMenuWorkspaceKey` 明确当前工作台目录，而不是靠 UI 行为隐式推断。

3. 用纯函数解析菜单上下文
   - 以 `resolveRuoyiMenuContext(pathname, menuData)` 作为统一的上下文解析入口。
   - 所有刷新恢复、租户切换恢复、首页跳转恢复，统一复用该函数。

4. 避免过度设计
   - 没有引入独立“导航中心”或复杂全局状态机。
   - 只在现有运行时布局、菜单适配层和少量入口页面中做轻量重构。

## 3. 本轮改造解决的问题

### 3.1 工作台菜单模式

已实现：

- 通过环境变量 `UMI_APP_MENU_WORKSPACE_NAMES` 指定哪些目录型菜单属于“工作台目录”。
- 这些目录会从默认左侧菜单中剔除。
- 这些目录会在头像下拉菜单中展示。
- 点击目录后，左侧只显示该目录的子菜单。

业务意义：

- 默认导航聚焦主业务路径，避免左侧菜单过长。
- 将后台配置类、账户类、系统类目录收敛到右上角工作台入口，更符合“顶级工作台切换 + 左侧局部菜单”的交互模式。

### 3.2 刷新后菜单恢复

已实现：

- 在应用初始化阶段，根据当前 `pathname` 与后端菜单树解析当前菜单模式。
- 若当前路径命中了某个工作台目录下的页面，则自动恢复为 `workspace` 模式。
- 若当前路径属于默认菜单，则自动恢复为 `default` 模式。

业务意义：

- 刷新页面后，左侧菜单与右侧内容重新保持一致。
- 用户不再看到“页面在系统管理，但左侧还显示默认业务菜单”的错位。

### 3.3 超管切租户后的菜单恢复

已实现：

- 超管切换租户后，清空菜单缓存。
- 重新拉取新租户菜单树。
- 基于当前路径和新菜单树重新解析菜单上下文。
- 如果原路径在新租户仍可访问，则尽量保持原路径。
- 如果原路径在新租户不可见，则回退到当前上下文的首页。

业务意义：

- 菜单与租户上下文重新对齐。
- 避免“切租户后页面内容和左侧菜单属于不同菜单树”的问题。

### 3.4 首页与占位页返回逻辑统一

已实现：

- `/` 首页不再简单跳第一个可见菜单，而是按当前菜单上下文回到正确首页。
- 占位页“返回业务首页”也接入同一套菜单上下文解析逻辑。

业务意义：

- 用户从未迁移页面、占位页、根路由回首页时，行为一致。
- 避免局部页面偷偷走回旧逻辑，造成上下文再次失真。

## 4. 核心实现方案

### 4.1 菜单上下文解析器

核心文件：`src/adapters/ruoyi/menu.tsx`

新增核心类型：

- `RuoyiMenuWorkspace`
- `RuoyiMenuWorkspaceMode`
- `RuoyiMenuContext`

新增核心能力：

1. `resolveRuoyiMenuWorkspaces`
   - 从完整菜单树中解析出配置命中的“工作台目录”。

2. `omitWorkspaceRootMenus`
   - 将工作台目录根菜单从默认左侧菜单中剔除。

3. `getVisibleRuoyiMenuData`
   - 根据当前模式（`default` / `workspace`）派生最终要展示的左侧菜单。

4. `resolveRuoyiMenuContext`
   - 给定当前 `pathname` 和菜单树，推导：
     - 当前菜单模式
     - 当前工作台 key
     - 当前可见菜单
     - 当前上下文首页路径
     - 当前命中的菜单项

这是本轮改造最关键的抽象。它把“导航上下文”从内存态提升为一个可重复推导的纯函数结果。

### 4.2 应用初始化恢复链路

核心文件：`src/app.tsx`

`getInitialState()` 的职责被扩展为：

1. 如果不是登录页，先尝试恢复动态租户上下文。
2. 再拉当前用户信息。
3. 再加载菜单树。
4. 再用 `resolveRuoyiMenuContext()` 根据当前路径恢复：
   - `menuWorkspaceMode`
   - `activeMenuWorkspaceKey`
   - `menuContextPathname`

同时在布局运行时新增了：

1. `syncMenuContextFromPath(pathname)`
   - 路由变化时，基于当前路径同步菜单上下文。

2. `menu.params` 增加 `menuContextPathname`
   - 让 `ProLayout` 的菜单请求真正能感知“当前菜单上下文路径”的变化。

3. `menu.request`
   - 不再主要依赖纯内存态决定菜单，而是用 `resolveRuoyiMenuContext(pathname, menuData)` 重新派生最终左侧菜单。

### 4.3 头像下拉工作台切换

核心文件：`src/components/RightContent/AvatarDropdown.tsx`

改造点：

1. 初始化时加载工作台目录列表。
2. 如果当前 `workspaceKey` 在新菜单树中已不存在，则自动回退到默认模式。
3. 点击工作台目录时，除更新：
   - `activeMenuWorkspaceKey`
   - `menuWorkspaceMode`
   之外，还同步写入：
   - `menuContextPathname`

这样做的原因是：

- 菜单模式变化与页面跳转必须保持同一个“目标路径语义”。
- 否则可能出现页面已经跳到工作台页面，但菜单还用旧上下文渲染的时序问题。

### 4.4 超管租户切换后的上下文恢复

核心文件：`src/components/TenantSwitch/index.tsx`

改造点：

1. 切租户后先清理菜单缓存。
2. 重新加载新租户菜单树。
3. 对当前路径调用 `resolveRuoyiMenuContext()`。
4. 计算 `nextPath`：
   - 优先当前路径
   - 次优当前上下文首页
   - 最后回退 `/`
5. 将以下状态同步写回 `initialState`：
   - `dynamicTenantId`
   - `tenantSwitchVersion`
   - `activeMenuWorkspaceKey`
   - `menuWorkspaceMode`
   - `menuContextPathname`

这保证了切租户后的“菜单模式、可见菜单、当前页面”三者尽可能一致。

### 4.5 首页与占位页统一

核心文件：

- `src/pages/ruoyi/landing/index.tsx`
- `src/pages/ruoyi/placeholder/index.tsx`

改造点：

1. 根路由 `/`
   - 不再简单取第一个菜单路径。
   - 改为按 `resolveRuoyiMenuContext()` 的 `homePath` 统一跳转。

2. 占位页“返回业务首页”
   - 改为按当前路径解析上下文首页，再回跳。

这一步虽然改动不大，但很重要，因为如果这些入口继续走旧逻辑，就会把前面恢复好的菜单上下文再次打乱。

## 8. 当前仍未彻底解决的问题

### 8.1 `/sys/settle` 刷新后数据看起来仍像不是当前租户

这部分**未在本轮提交中修复**，但已经完成了较完整的根因分析。

当前判断如下：

1. `/sys/settle` 前端页面本身没有自己缓存租户数据。
2. `/sys/settle` 对应的主查询接口，大多也已经显式按 `tenantId` 过滤。
3. 动态租户本身在后端是持久化的，不是刷新就天然丢失。
4. 因此 `/sys/settle` 更大的可疑点在于：
   - 其依赖的源数据表在写入阶段就写错了 `tenant_id`
   - 或 `recov` 模块内部某些写路径仍直接使用 `LoginHelper.getTenantId()`，没有走动态租户优先的 `TenantHelper.getTenantId()`

也就是说：

- `/sys/settle` 当前更像是“读取到了错误归属的源数据”
- 而不是“页面刷新时把租户切错了”

### 8.2 `/sys/settle` 的具体排查结论

已确认：

1. `ServiceFeeSettlementServiceImpl` 的主读接口使用的是 `TenantHelper.getTenantId()`。
2. `ServiceFeeSettlementMapper.xml` 和 `DebtRepaymentRecordMapper.xml` 多数查询都显式写了 `WHERE tenant_id = #{tenantId}`。
3. 周结算任务生成结算单时也会显式设置 `settlement.setTenantId(tenantId)`。

因此 `/sys/settle` 当前最可疑的剩余方向是：

1. `debt_repayment_record`
2. `debt_repayment_detail`

这两张源表的写入链路需要继续向前追，确认写入时的 `tenant_id` 来源是否统一使用了动态租户优先逻辑。

## 9. 下一步建议

如果后续继续处理 `/sys/settle`，建议不要再改前端，而是直接继续做后端写链路核查：

1. 追 `debt_repayment_record` 的创建入口。
2. 追 `debt_repayment_detail` 的创建入口。
3. 确认写入时 `tenant_id` 到底来自：
   - `TenantHelper.getTenantId()`
   - 还是 `LoginHelper.getTenantId()`
4. 如果存在直接使用 `LoginHelper.getTenantId()` 的业务写路径，应统一改为动态租户优先逻辑。

## 10. 结论

本轮改造从业务上完成了两个关键目标：

1. 菜单从“单一全量树”重构为“默认菜单 + 工作台目录”的双视图模式。
2. 菜单上下文从“纯内存态”重构为“可从 URL 和菜单树恢复”的显式上下文模型。

这解决了：

- 工作台目录切换
- Logo 返回默认菜单
- 刷新后菜单恢复
- 超管切租户后的菜单恢复
- 首页与占位页回退逻辑不统一

但 `/sys/settle` 的租户数据错位问题不属于这轮前端菜单改造的直接范围，当前更接近后端数据写入租户归属问题，后续应按后端写链路继续定位，而不是继续在前端补丁式兜底。
