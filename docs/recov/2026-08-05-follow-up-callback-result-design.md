# 跟进回拨与提交处理结果设计

## 1. 目标与范围

将“登记联系结果、完成任务、关闭任务”收敛为一次 **提交处理结果**。一次提交同时保存本次联系记录，并明确跟进任务的下一步，避免列表上出现含义重叠的三个动作。

本期只覆盖：跟进任务列表、人工回拨后的处理结果、回拨通话详情与关联历史。

不覆盖：自动提醒、AI 对回拨通话的自动分析、外呼策略重试、19011 的端口/配置/进程改造。

## 2. 已确认的业务规则

### 2.1 任务状态

| 当前状态 | 操作 | 结果状态 | 规则 |
| --- | --- | --- | --- |
| 待认领 | 认领回访 | 处理中 | 负责人固定为当前坐席 |
| 处理中 | 提交处理结果：继续跟进 | 处理中 | 必须填写下次跟进时间 |
| 处理中 | 提交处理结果：办结任务 | 已完成 | 已达成业务目的，不再跟进 |
| 处理中 | 提交处理结果：终止跟进 | 已关闭 | 不应继续跟进，必须填写终止原因和处理备注 |

“办结任务”表示业务已完成；“终止跟进”表示明确停止，例如客户拒绝、联系方式无效、任务误创建。两者都由“提交处理结果”产生，不再作为列表上的独立按钮。

### 2.2 联系结果与下一步

| 联系结果 | 可选下一步 | 额外要求 |
| --- | --- | --- |
| 已接通 | 继续跟进、办结任务、终止跟进 | 处理备注必填 |
| 无人接听、占线、技术失败 | 继续跟进 | 下次跟进时间必填；技术失败说明必填 |
| 客户拒接、联系方式无效 | 继续跟进、终止跟进 | 终止时填写终止原因和处理备注 |

每次提交都保存处理备注。对未接通结果，表单预填“本次回拨未接通”，坐席可补充；对已接通，必须由坐席填写本次沟通结论。

### 2.3 回拨未接通

回拨结束后，系统先自动生成一条与 `call_id` 关联的回拨尝试记录，任务仍保持“处理中”。坐席随后只需提交下一步；默认“继续跟进”，并选择下次跟进时间。

若坐席关闭页面或浏览器断开，自动生成的通话结果仍保留，任务不自动办结或关闭。坐席下次打开该任务时可补交处理结果。

## 3. 页面交互

### 3.1 跟进任务列表

保留两个 Tab：`待认领回访`、`我的跟进`。筛选区沿用外呼任务的紧凑布局，只保留常用条件：创建日期、业务场景、回访状态、客户姓名。

列表字段依次为：客户（姓名 + 脱敏手机号）、所属任务、创建时间、跟进原因、应跟进时间、最近联系结果、回访状态、操作。客户姓名来自发起外呼时的名单；确实缺失时只展示脱敏手机号，不展示“客户姓名未提供”。不展示业务编号、`handoff_id`、`call_id` 等原始标识。

“我的跟进”的操作为：`查看详情`、`上线并呼叫/呼叫客户`、`提交处理结果`。三个操作均使用现有“查看详情”同款文字链接样式；终态任务只保留查看详情。

### 3.2 提交处理结果弹窗

弹窗字段按顺序为：

1. 联系结果：回拨产生时由本次通话最终状态带入，只读；非电话联系时可选择。
2. 处理备注：必填；未接通自动预填结果说明。
3. 下一步：继续跟进、办结任务、终止跟进。
4. 下次跟进时间：仅“继续跟进”显示且必填。
5. 终止原因：仅“终止跟进”显示且必填。

提交成功使用短暂 Toast 提示，刷新当前列表并关闭弹窗。提交失败保留已填写内容和错误提示，不能在前端提前改变任务状态。

## 4. 回拨通话详情

回拨是人工坐席与客户的直接通话，不沿用 AI 外呼详情的信息结构。

详情顺序固定为：

1. 本次回拨：客户、所属跟进任务、原始通话、坐席、开始时间、时长、结束状态。
2. 录音与对话：复用通话记录详情的气泡样式；“人工坐席：内容”和“客户：内容”各自放在同一个气泡内。仅右侧对话区滚动，不让整个页面为对话产生额外滚动。
3. 关联通话与处理记录：原始通话和每次人工回拨放入同一条时间线；回拨条目展示接通结果、处理备注和下一步。当前回拨高亮。

本期移除回拨详情中的“AI 分析”“转人工记录”“本次处理结果”独立模块，避免与人工提交内容重复。处理结果只在“关联通话与处理记录”的对应回拨条目出现。

示例条目：`2026-08-05 15:20 · 坐席 agent-admin · 已接通 · 备注：客户说下午再联系 · 下一步：继续跟进`。

## 5. 数据与接口约定

### 5.1 统一提交接口

新增一个原子接口，替代前端依次调用“登记尝试、完成、关闭”：

```http
POST /agent-console/follow-ups/{followUpId}/handling-results
Idempotency-Key: <uuid>
```

```ts
type FollowUpNextAction = 'continue' | 'complete' | 'close';

type SubmitFollowUpHandlingResultInput = {
  callId?: string;
  contactChannel?: 'manual_phone' | 'wechat' | 'email' | 'other';
  contactResult: 'connected' | 'no_answer' | 'busy' | 'rejected' | 'invalid_contact' | 'technical_failure';
  remark: string;
  nextAction: FollowUpNextAction;
  nextFollowUpAt?: string;
  closedReason?: 'customer_refused' | 'invalid_contact' | 'created_by_error' | 'no_longer_needed' | 'other';
};
```

后端在同一事务内完成：校验负责人和任务状态、写入或补全本次联系记录、写入处理记录、更新下一次跟进时间、更新任务状态。相同幂等键重复提交返回第一次的结果，不重复写入记录。

对于人工回拨，`callId` 必填，接口校验该通话已结束且归属该跟进任务；联系人结果以通话最终结果为准，拒绝前端篡改。对于微信、邮件等非电话联系，不传 `callId`，由坐席填写联系结果。

现有 `attempts`、`complete`、`close` 接口本期不从新页面调用；是否删除由后端实际调用方审计后另行决定。

### 5.2 详情返回字段

跟进详情需返回：客户姓名、脱敏手机号、所属任务名称、原始通话、回拨通话列表、每次回拨对应的最终通话状态、联系结果、处理备注、下一步、下次跟进时间、处理人、处理时间。

所有业务 ID 继续按字符串传输，只用于接口关联和跳转，不作为默认可见字段。

## 6. 异步、异常与重试

- “呼叫客户”成功只表示回拨已受理；通话状态由现有事件/刷新链路更新，不能立即当作已接通。
- 通话结束但处理结果尚未提交时，任务保持处理中，并在列表上提示“待提交处理结果”。
- 回拨通话详情与任务详情任一加载失败时，保留当前抽屉和返回路径，提供局部重试；不跳转离开跟进上下文。
- 处理结果提交使用幂等键；网络超时后允许用同一业务操作重试，服务端不得重复生成处理记录。
- 录音、对话或原始通话缺失应分别显示“暂无”，不影响已存在的处理记录展示。

## 7. 19011 边界

本设计不要求修改 19011 的端口、环境变量、启动方式、SIP/LiveKit 配置或真实外呼链路。

完整落地时，`handling-results` 是后端服务的新业务接口，因此需要在后端代码中实现并由现有 API 服务提供；这属于接口能力开发，不是环境改造。前端可先完成列表、详情和表单收口，但在该接口可用前不能宣称“处理记录与状态流转已原子闭环”。

## 8. 验收标准

- 列表不再同时出现完成、关闭、登记联系结果三个动作。
- 一次提交可明确保存联系结果、备注和任务下一步，重复提交不产生重复记录。
- 未接通不会自动办结；继续跟进必须有下次跟进时间。
- 每次回拨都能在同一任务详情中看到通话与对应处理记录，且可进入通话详情后返回。
- 回拨详情只展示人工通话所需信息，不展示 AI 分析和重复的独立处理结果模块。
- 前端筛选与列表字段不暴露无业务价值的原始编号。
