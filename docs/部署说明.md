# 前端开发与部署说明

## 1. 边界与原则

本前端保持一套源码和一份构建产物。不同产品站点通过服务端站点配置选择登录布局，不为不同域名复制前端仓库，也不因 Logo、登录布局、租户模式或 TLS 证书不同重复构建 dist。

这里需要区分“前端通用能力”与“当前正式发布能力”：

- 前端代码已经具备登录布局注册、同源逻辑 API 通道和同一 dist 复用到不同站点的能力模型。
- 当前 `lingchen-release` 正式链路只生成 `baseApi` 和遗留兼容字段 `adminApi`，两条路径均由正式 Web 配置转发到 Gateway/Backend Ingress；正式链路尚未生成独立 `productApi` 或 `voiceApi`，也不管理独立 Product/Voice upstream。
- 当前每个 Backend 或 Web 角色包只管理一个站点配置。一个 dist 可服务多个域名是前端能力模型，但“一个正式安装自动编排多个域名、多个站点配置”目前尚未实现。

因此，下文关于 `productApi`、`voiceApi` 和多域名复用的描述是前端契约与扩展边界，不能理解为当前 `lingchen-release` 已经能够自动部署这些拓扑。

安全边界如下：

- 生产登录布局由 `GET /auth/site/config` 返回，前端不根据可篡改的 URL 参数选择生产布局。
- `X-Lingchen-Product-Code` 由受信 Web 代理覆盖，浏览器不提交可信产品编码。
- `FIXED` 站点登录时前端不提交 `tenantId`，由 Auth 使用服务端解析的标准租户。
- `SELECTABLE` 站点才加载和显示租户列表。
- `clientId` 继续来自前端运行时配置，Auth 负责校验它与当前产品站点匹配。
- 菜单隐藏不是授权。产品、租户套餐、菜单、接口权限和许可证必须由后端最终校验。

## 2. 站点配置契约

匿名站点接口的数据契约为：

```ts
type SiteConfig = {
  productCode?: string;
  productName?: string;
  loginVariant: string;
  tenantMode: 'SELECTABLE' | 'FIXED';
};
```

公共基座站点返回 `loginVariant=default`、`tenantMode=SELECTABLE`。产品站点可返回其已注册布局和 `FIXED` 租户模式。

如果服务端返回未注册的 `loginVariant`，前端显示明确的站点配置错误和当前支持值，不静默回退到其他产品登录页。

## 3. 新增登录布局

当前只注册 `default` 布局。新布局必须复用 [controller.ts](../src/pages/user/login/controller.ts) 中的验证码、站点配置、租户、登录、Token、重定向和错误处理，只实现展示差异。

新增步骤：

1. 新建实现 `LoginLayoutProps` 的布局组件。
2. 在 [catalog.json](../src/pages/user/login/layouts/catalog.json) 增加编码和显示名称。
3. 在 [registry.ts](../src/pages/user/login/layouts/registry.ts) 的组件表中增加 `React.lazy(() => import(...))`。
4. 执行登录布局注册表测试，确保 catalog 和懒加载组件一一对应。

编码必须符合：

```text
^[a-z][a-z0-9-]{0,63}$
```

`AUTO`/`auto` 为保留值，不能注册为布局编码。catalog 与组件映射任何一边遗漏、重复或格式非法，都应在测试或启动时失败。

## 4. 本地开发

### 4.1 交互式配置

执行：

```bash
npm run configure:local
```

向导会一次收集：

- 登录布局：`AUTO` 或从 catalog 动态列出的显式布局。
- 本地产品编码：可留空；非空时必须符合 `[A-Z][A-Z0-9_]{1,63}`，输入会规范为大写。
- Gateway：必填的浏览器同源路径和本地后端目标。
- Product API：可选的逻辑后端通道。
- Voice API：可选的逻辑后端通道。

全部输入完成后，向导先统一展示配置，再并发检查所有已选后端。任意 HTTP 状态码都表示网络已连通；超时、连接失败、DNS 失败或 TLS 验证失败会汇总列出。如有失败，用户必须明确选择“返回修改”、“仍然保存”或“取消”。

向导只原子更新已明确列入受管范围的 `.env.local` 键，保留其他本机配置。`.env.local` 已被 Git 忽略，不得提交。

### 4.2 启动

```bash
npm run dev
```

`npm run dev` 使用 `UMI_ENV=dev`、禁用 Mock，并自动读取 `.env.local`。`npm start` 会保留 Mock，不用于真实后端联调。

本地选择显式布局只是开发覆盖。生产构建会忽略该覆盖，始终使用服务端站点配置。

本地没有生产 Web 代理时，Umi Proxy 会在 Gateway、SSE 以及所有启用通道上固定覆盖 `X-Lingchen-Product-Code`。留空表示公共基座，因此 `AUTO` 也能在本地获取指定产品的 `/auth/site/config`。该本地键不注入浏览器代码。

## 5. 多后端 API 通道

前端使用逻辑通道，不在页面中保存后端机器地址：

| 通道 | 前端用途 | 是否必需 |
|---|---|---|
| Gateway / `baseApi` | Auth、System、Resource及Gateway已路由的产品Java服务 | 是 |
| Product / `productApi` | Gateway之外的产品后端 | 否 |
| Voice / `voiceApi` | 实时外呼网关 | 否 |

一个产品Java模块如果已由Gateway路由，不应再为它增加独立浏览器API通道。仅Gateway之外的真实独立服务才新增通道。

本地的绝对后端目标只存在 `.env.local` 并由 Umi Proxy 使用。生产的真实 upstream 只存在 Web/Nginx 服务端配置中。浏览器只获得同源路径，避免 CORS、内网地址暴露和多套凭据策略。

Voice 页面已通过统一 Voice API 适配器访问。未配置该可选通道时，会明确报错，不会意外发送到站点根路径或 Gateway。

以上是前端通用通道模型。当前正式 release 不会创建独立 Product/Voice upstream；它只下发 `baseApi` 与 `adminApi`，并由既有 Gateway/Backend Ingress 承接。若以后正式支持独立通道，必须同步改造 release manifest、Web/Nginx upstream、交互配置、preflight 和验证链路，不能只在 `runtime-config.js` 中增加路径。

## 6. 生产 runtime-config.js

生产在前端应用脚本执行前同步加载 `runtime-config.js`。当前契约支持：

```text
schemaVersion
baseApi
productApi       可选
adminApi         遗留的Product通道字段，与productApi二选一
voiceApi         可选
ssePath
clientId
encrypt
requestRsaPublicKey  开启请求加密时必填
```

`productApi` 和 `adminApi` 是同一逻辑通道的新旧字段，必须二选一；同时配置会因语义不明确而被前端拒绝。当前 `lingchen-release` 仍只生成 `adminApi`，尚未切换到 `productApi`，也不会生成 `voiceApi`。

`baseApi`、`productApi/adminApi`和`voiceApi`必须是不同的同源绝对路径，不能使用站点根路径。生产配置缺失、字段未知、路径非法或加密契约不完整时，前端拒绝启动请求链路。

不得写入 `runtime-config.js` 的内容：

- `tenantId`或可信产品编码；
- 私钥、密码、Token和后端Secret；
- 内网后端绝对地址；
- 本地显式登录布局覆盖。

## 7. 域名、IP 和 HTTPS

- 域名、端口、TLS 证书和后端 upstream 属于 Web 部署配置，不进入前端 dist。
- 从前端能力看，同一份 dist 可由多个域名提供，但每个生产站点必须由受信Web代理生成正确的产品上下文。当前正式角色包一次只管理一个站点，正式多域名/多站点编排尚未实现。
- 用IP直接访问时，必须明确它应归属哪个站点；否则应视为公共基座或拒绝，不根据浏览器参数推断产品。
- HTTPS 由 Web/Nginx 终止。前端 API 始终使用同源路径，因此 HTTP 切换为 HTTPS 不需要重新构建前端。
- 证书SAN、DNS、防火墙、安全组和客户端信任链由部署工具与运维检查，不由React应用检查。

## 8. 更新边界

| 变更 | 是否重新构建前端 |
|---|---|
| 后端独立更新，API契约仍兼容 | 否 |
| 域名、端口、TLS证书、Nginx upstream | 否 |
| 同源 API 路径变更 | 否，但必须原子更新runtime-config和Nginx |
| 产品到已有登录布局的映射 | 否，由服务端站点配置变更 |
| 新增登录布局、页面或静态资源 | 是 |
| 前后端 API 契约不兼容 | 是，并必须协调发布顺序 |

只更新后端时，Web 可保持上一个前端Tag；不得将“后端可独立更新”解释为允许忽略API契约兼容性。
