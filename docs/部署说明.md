# 前端开发与部署说明

## 1. 边界与原则

本前端保持一套源码和一份构建产物。不同产品站点通过服务端站点配置选择登录布局，不为不同域名复制前端仓库，也不因 Logo、登录布局、租户模式或 TLS 证书不同重复构建 dist。

这里需要区分“前端能力模型”与“当前正式发布能力”：

- 前端代码已经具备登录布局注册、一个主 API 和同一 dist 复用到不同站点的能力模型；当前没有浏览器直连 API。
- 当前 `lingchen-release` 正式链路生成 `baseApi` 和遗留兼容字段 `adminApi`。前端为兼容正式配置仍解析 `adminApi`，但所有业务请求只使用 `baseApi`，不会把它暴露为第二套业务 API。
- 当前 `lingchen-release` 固定生成 `infra` 与 `app` 两个签名包；`app` 同时包含公共后端、所选产品、Backend Ingress 与 Web，并且一次只管理一个站点配置。一个 dist 可服务多个域名是前端能力模型，但“一个正式安装自动编排多个域名、多个站点配置”目前尚未实现。

安全边界如下：

- 生产登录布局由 `GET /auth/site/config` 返回，前端不根据可篡改的 URL 参数选择生产布局。
- `X-Lingchen-Product-Code` 由受信 Web 代理覆盖，浏览器不提交可信产品编码。
- `FIXED` 站点登录时前端不提交 `tenantId`，由 Auth 使用服务端解析的标准租户。
- `SELECTABLE` 站点才加载和显示租户列表。
- `clientId` 继续来自前端运行时配置，Auth 负责校验它与当前产品站点匹配。
- 已登录用户访问普通业务页面时，以 `GET /system/menu/getRouters` 返回的原始完整路由树作为白名单，包括 `hidden` 路由；授权加载失败时 fail-closed。
- `hideInMenu` 和后端 `activeMenu` 只控制展示与高亮，不授予路由权限；前端不根据父路径或产品编码推断准入。
- 敏感页面的 Umi `access` 只能进一步收紧授权，不能绕过后端路由白名单。
- 页面按钮权限码和后端接口鉴权分别执行，产品、租户套餐、权限和许可证仍由后端最终校验。

## 2. 站点配置契约

匿名站点接口的数据契约为：

```ts
type SiteConfig = {
  productCode?: string;
  productName?: string;
  loginVariant: string;
  tenantMode: 'SELECTABLE' | 'FIXED';
};
```

公共基座站点返回 `loginVariant=default`、`tenantMode=SELECTABLE`。产品站点可返回其已注册布局和 `FIXED` 租户模式。

如果服务端返回未注册的 `loginVariant`，前端显示明确的站点配置错误和当前支持值，不静默回退到其他产品登录页。

## 3. 新增登录布局

当前只注册 `default` 布局。新布局必须复用 [controller.ts](../src/login-layouts/controller.ts) 中的验证码、站点配置、租户、登录、Token、重定向和错误处理，只实现展示差异。

新增步骤：

1. 新建实现 `LoginLayoutProps` 的布局组件。
2. 在 [catalog.json](../src/login-layouts/catalog.json) 增加编码和显示名称。
3. 在 [registry.ts](../src/login-layouts/registry.ts) 的组件表中增加 `React.lazy(() => import(...))`。
4. 执行登录布局注册表测试，确保 catalog 和懒加载组件一一对应。

编码必须符合：

```text
^[a-z][a-z0-9-]{0,63}$
```

`AUTO`/`auto` 为保留值，不能注册为布局编码。catalog 与组件映射任何一边遗漏、重复或格式非法，都应在测试或启动时失败。

## 4. 本地开发

### 4.1 交互式配置

执行：

```bash
npm run configure:local
```

向导会一次收集：

- 登录布局：`AUTO` 或从 catalog 动态列出的显式布局。
- 本地产品编码：可留空；非空时必须符合 `[A-Z][A-Z0-9_]{1,63}`，输入会规范为大写。
- Gateway：必填的浏览器同源路径和本地后端目标。
- Web `clientId`：默认使用后端和正式 release 的标准 PC Web 客户端，可按本地 `sys_client` 调整。
- API 请求加密：必须与本地后端 `api-decrypt` 配置一致；当前标准后端登录接口要求加密，因此默认开启。开启时必须提供与后端解密私钥配对、至少 2048 位的 Base64 DER SPKI RSA 公钥。

该公钥必须从本地后端实际使用的 `api-decrypt.private-key` 导出，不能沿用示例公钥；私钥本身不得写入前端 `.env.local`。向导会校验公钥类型和位数，但不会展示已保存的完整公钥。

全部输入完成后，向导先统一展示配置，再并发检查所有已选后端。任意 HTTP 状态码都表示网络已连通；超时、连接失败、DNS 失败或 TLS 验证失败会汇总列出。如有失败，用户必须明确选择“返回修改”、“仍然保存”或“取消”。

向导只原子更新已明确列入受管范围的 `.env.local` 键，保留其他本机配置。`.env.local` 已被 Git 忽略，不得提交。

### 4.2 启动

```bash
PORT=8001 npm run dev
```

`npm run dev` 使用 `UMI_ENV=dev`、禁用运行时 Mock，并自动读取 `.env.local`。项目不再提供会启用运行时 Mock 的启动脚本。

本地选择显式布局只是开发覆盖。生产构建会忽略该覆盖，始终使用服务端站点配置。

生产构建会把已知的 `UMI_APP_*` 本地覆盖固定为空值，不把构建机的 API、clientId、RSA、登录布局或菜单分组写入 dist；这些值只允许非生产开发构建使用。正式站点值必须由部署时生成的 `runtime-config.js` 提供。

本地没有生产 Web 代理时，Umi Proxy 会在 Gateway 和 SSE 路径上固定覆盖 `X-Lingchen-Product-Code`。留空表示公共基座，因此 `AUTO` 也能在本地获取指定产品的 `/auth/site/config`。该本地键不注入浏览器代码。

## 5. 主 API

当前所有浏览器业务请求统一使用 `src/api/main.ts`，由主 Gateway 转发。页面和业务模块只传后端真实业务路径，不保存后端机器地址，也不按产品、管理员或业务类型创建 API 通道。

| 通道 | 前端用途 | 是否必需 |
|---|---|---|
| Gateway / `baseApi` | Auth、System、Resource及Gateway已路由的产品Java服务 | 是 |

正式 release 仍下发 `adminApi`，但它只是配置解析兼容字段，前端业务请求忽略它，不构成第二条业务通道。新正式链路停止生成该字段后，前端才能移除解析兼容。

本地的绝对后端目标只存在 `.env.local` 并由 Umi Proxy 使用。生产的真实 upstream 只存在 Web/Nginx 服务端配置中。浏览器只获得同源路径，避免 CORS、内网地址暴露和多套凭据策略。

Recov 智能外呼的统计、记录、详情和分析通过主 API 获取；`/sys/voice` 保留为音色、数字员工和外呼并发等业务配置页面，也只调用主 API。它们都不需要独立 Voice upstream。

不为未来产品或服务预建 API 类型。只有新 upstream 被证明无法由主 Gateway 承接时，才在明确的所有者模块下设计对应直连 API，并同步实现同源代理、认证、401、审计、错误契约、release manifest、Web/Nginx upstream、preflight 和部署验证；只在 `runtime-config.js` 中增加路径不构成正式能力。

## 6. 生产 runtime-config.js

生产在前端应用脚本执行前同步加载 `runtime-config.js`。当前契约支持：

```text
schemaVersion
baseApi
adminApi         遗留正式配置兼容字段，业务请求忽略
ssePath
clientId
encrypt
requestRsaPublicKey  开启请求加密时必填
```

当前 `lingchen-release` 仍生成 `adminApi`，因此前端解析器暂时允许该字段，但不会把它暴露为第二套业务 API。新正式链路停止生成该字段后，可再移除这层解析兼容。

`baseApi`、遗留 `adminApi` 和 `ssePath` 必须是安全的同源绝对路径，不能使用站点根路径；`baseApi` 和 `adminApi` 不能相同。浏览器最终使用的 SSE 路径（`ssePath` 已位于 `baseApi` 下时直接使用，否则拼接为 `baseApi + ssePath`）也不能与 `baseApi` 或遗留 `adminApi` 冲突。生产配置缺失、字段未知、路径非法、通道冲突或加密契约不完整时，前端拒绝启动请求链路。

普通 `npm run build` 只生成待部署的静态产物，其中不写入可用的生产运行时配置。仓库不提供裸 `preview` 脚本；正式预览必须先由受信部署工具生成 `runtime-config.js` 与匹配的同源代理配置，不能通过放宽生产校验来绕过。

当前仍有两项需要在 `lingchen-release` 另仓同步的纵深加固，不属于本仓已实现能力：

- 候选配置与 Nginx renderer 应在安装前按同一算法拒绝 SSE 最终路径与 `baseApi`、`adminApi` 的精确 location 冲突；本前端已在运行时 fail-closed，但不能代替部署预检。
- 正式构建器应清空或拒绝继承的 `UMI_APP_*`，作为前端中性 define 之外的第二道防线。

不得写入 `runtime-config.js` 的内容：

- `tenantId`或可信产品编码；
- 私钥、密码、Token和后端Secret；
- 内网后端绝对地址；
- 本地显式登录布局覆盖。

## 7. 域名、IP 和 HTTPS

- 域名、端口、TLS 证书和后端 upstream 属于 Web 部署配置，不进入前端 dist。
- 从前端能力看，同一份 dist 可由多个域名提供，但每个生产站点必须由受信Web代理生成正确的产品上下文。当前正式 App 包一次只管理一个站点，正式多域名/多站点编排尚未实现。
- 用IP直接访问时，必须明确它应归属哪个站点；否则应视为公共基座或拒绝，不根据浏览器参数推断产品。
- HTTPS 由 Web/Nginx 终止。前端 API 始终使用同源路径，因此 HTTP 切换为 HTTPS 不需要重新构建前端。
- 证书SAN、DNS、防火墙、安全组和客户端信任链由部署工具与运维检查，不由React应用检查。

## 8. 更新边界

| 变更 | 是否需要修改前端源码 |
|---|---|
| 后端更新，API契约仍兼容 | 否，可继续锁定上一前端 Tag |
| 域名、端口、TLS证书、Nginx upstream | 否 |
| 同源 API 路径变更 | 否，但必须原子更新runtime-config和Nginx |
| 产品到已有登录布局的映射 | 否，由服务端站点配置变更 |
| 新增登录布局、页面或静态资源 | 是 |
| 前后端 API 契约不兼容 | 是，并必须协调发布顺序 |

这里的“否”只表示不需要修改前端源码。当前正式 `lingchen-release` 不支持仅后端角色包：每次正式构建仍固定生成 `infra` 与 `app` 双包，并对锁定的前端版本执行安装、构建和 Web 镜像重建后纳入 App 包。不得将“前端 Tag 可保持不变”误解为可以跳过正式 Web 制品构建，也不得忽略 API 契约兼容性。
