# AI Call 通话记录客户意向与跟进状态设计

## 1. 文档状态

- 设计日期：2026-07-30
- 设计状态：方案已确认，等待书面规格审查
- 实施状态：未开始
- 适用范围：AI Call 通话记录列表、通话详情和跟进任务管理的关联展示

## 2. 目标

在通话记录列表中同时展示“客户意向”和“跟进状态”，让运营人员能够快速回答两个不同问题：

1. 客户在本次通话中的态度和意向是什么。
2. 本次通话是否已经形成真实跟进任务，以及任务处理到什么阶段。

两类信息必须分开呈现，不能把 AI 分析结果误报为已经创建的业务任务。

## 3. 非目标

- 不在列表中展示全部语义分析标签。
- 不从摘要、关键点或自由文本标签中临时猜测跟进状态。
- 不在通话记录列表内新增创建、领取、回拨或关闭跟进任务的操作。
- 不改变外呼任务、拨打尝试、转人工或跟进任务的既有状态机。
- 不把忙线、无人接听等技术重拨结果当作人工跟进任务。
- 不为 Mock 通话创建真实跟进任务或展示真实客户意向。

## 4. 信息架构

通话记录列表新增两个独立列：

| 列名 | 回答的问题 | 数据来源 |
| --- | --- | --- |
| 客户意向 | 客户对本次沟通的态度如何 | 结构化语义分析结果 |
| 跟进状态 | 是否已有跟进工作及其处理进度 | 结构化跟进建议和真实跟进任务 |

现有“通话摘要”列继续展示摘要文本，不承载意向或跟进任务状态。

列表中每列最多显示一个主标签。价格敏感、关注产品、要求报价等细粒度语义标签只在通话详情中展示。

## 5. 客户意向

### 5.1 字段契约

列表接口返回以下稳定字段，前端不得解析中文摘要推导意向：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `analysisStatus` | string | 当前语义分析状态 |
| `customerIntent` | string 或 null | 分析完成后的结构化客户意向 |

`customerIntent` 支持：

| 值 | 列表文案 | 标签颜色 |
| --- | --- | --- |
| `positive` | 正向 | `success` |
| `neutral` | 中性 | `processing` |
| `negative` | 负向 | `error` |
| null | 根据 `analysisStatus` 决定 | 见下表 |

当 `customerIntent` 为空时：

| `analysisStatus` | 列表展示 |
| --- | --- |
| `pending` / `processing` | 灰色“待分析” |
| `failed` | 红色“分析失败” |
| `no_speech` / `not_applicable` | `-` |
| 未知值 | `-` |

“正向”只表示客户态度，不代表客户同意回访，也不代表跟进任务已经创建。

### 5.2 Mock 和未接通记录

- `entryType=outbound_mock` 时展示 `-`。
- 无人接听、忙线、号码无效等没有有效客户话术的记录展示 `-`。
- 不得为了填充列表而使用任务名称、客户名称或 AI 话术推测客户意向。

## 6. 跟进状态

### 6.1 字段契约

列表接口返回：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `followUpSuggested` | boolean | 统一话后结果是否建议跟进 |
| `followUpId` | string 或 null | 已创建的真实跟进任务 ID |
| `followUpStatus` | string 或 null | 真实跟进任务状态 |

所有 bigint 或业务 ID 返回前端时统一使用字符串。

`followUpSuggested` 必须来自统一的结构化话后结果。后端不得通过搜索摘要中的“联系”“回访”“有意向”等文字生成该值。

### 6.2 展示优先级

跟进状态按以下顺序计算：

1. 存在 `followUpId` 时，只展示真实任务状态。
2. 不存在 `followUpId` 且 `followUpSuggested=true` 时，展示“建议跟进”。
3. 其余情况展示 `-`。

真实任务状态优先于 AI 建议，不能同时显示“建议跟进”和“待跟进”。

| 条件 | 列表文案 | 标签颜色 |
| --- | --- | --- |
| 无任务且建议跟进 | 建议跟进 | `warning` |
| `followUpStatus=pending` | 待跟进 | `processing` |
| `followUpStatus=processing` | 跟进中 | `purple` |
| `followUpStatus=completed` | 已完成 | `success` |
| `followUpStatus=closed` | 已关闭 | `default` |
| 有 `followUpId` 但状态缺失或非法 | 状态异常 | `error` |
| 无任务且无需跟进 | `-` | 无标签 |

### 6.3 业务边界

- 客户明确提出后续联系且满足回访同意规则时，可以由后端规则自动创建跟进任务。
- 转人工无人接听时，可以按既有规则幂等创建“人工未接回访”任务。
- 坐席话后处理选择“需要跟进”时，可以按既有规则创建任务。
- AI 只识别出模糊正向意向时，最多展示“建议跟进”，不能假装任务已经创建。
- 忙线、无人接听等是否再次拨打由外呼任务重试策略负责，不进入跟进任务状态。
- 同一来源的重复事件由后端幂等处理，列表不能出现由重复任务导致的随机状态。

## 7. 前端交互

### 7.1 列表布局

- “客户意向”与“跟进状态”使用两个独立列。
- 每列只显示一个紧凑 `Tag`，不在单元格内换行堆叠多个语义标签。
- “通话摘要”继续最多显示两行，表格允许横向滚动，操作列继续固定在右侧。
- 无状态时显示 `-`，不展示“无需跟进”等低价值装饰标签。

建议列宽：

| 列名 | 宽度 |
| --- | --- |
| 客户意向 | 96 px |
| 跟进状态 | 112 px |

### 7.2 点击行为

- “正向 / 中性 / 负向 / 待分析 / 分析失败”标签点击后打开本次通话详情，并定位到 AI 分析区域。
- “建议跟进”点击后打开本次通话详情，并定位到话后结果或跟进建议区域。
- “待跟进 / 跟进中 / 已完成 / 已关闭”点击后进入跟进任务管理页，通过 `followUpId` 定位并打开对应任务详情。
- `-` 和“状态异常”不提供跳转；“状态异常”的完整原因通过悬浮提示展示。

跟进任务管理页需要支持 `followUpId` URL 参数。找不到对应任务时保留页面和筛选条件，并提示“关联跟进任务不存在或无权查看”，不能打开错误任务。

### 7.3 筛选

查询区新增：

| 筛选项 | 选项 |
| --- | --- |
| 客户意向 | 正向、中性、负向、待分析、分析失败 |
| 跟进状态 | 建议跟进、待跟进、跟进中、已完成、已关闭、无跟进 |

筛选必须由后端分页查询执行，前端不能只过滤当前页数据。

## 8. 数据流与刷新

通话记录列表接口一次返回列表展示所需的意向和跟进聚合字段，前端不得为每一行分别请求语义分析或跟进任务，避免 N+1 请求。

数据流：

```text
通话结束
  -> 转写与语义分析
  -> 结构化客户意向和话后结果
  -> 跟进规则判断
  -> 可选创建跟进任务
  -> 通话记录列表聚合返回
```

刷新规则：

- 首次进入、查询、重置和手动刷新时重新请求列表。
- 页面存在通话未结束或语义分析处于 `pending/processing` 的记录时，每 5 秒单飞刷新当前页。
- 上一轮请求未结束时跳过新的轮询，不堆积请求。
- 当前页全部进入稳定状态后停止自动轮询。
- 页面重新获得焦点时刷新一次，以同步在跟进任务页面发生的状态变化。
- 跟进任务后续长期处理状态不要求通话记录页持续轮询。

接口成功只代表取得当前快照，不代表语义分析或跟进工作已经完成。最终展示以随后查询到的稳定状态为准。

## 9. 异常处理

- 列表主请求失败时使用现有统一错误处理，不保留旧数据并伪装成最新状态。
- 单条记录缺少新增字段时降级为 `-`，不能根据摘要补算。
- `followUpId` 存在但 `followUpStatus` 非法时展示“状态异常”，便于发现数据不一致。
- 跟进任务详情无权访问时展示权限提示，不泄露客户信息。
- AI 分析失败仅影响客户意向和建议跟进，不得覆盖已经存在的真实跟进任务状态。
- 真实跟进任务完成后，即使语义分析重跑，列表仍展示“已完成”，不得回退成“建议跟进”。

## 10. 重试与幂等

- 通话记录列表查询失败只重试读取，不触发语义分析或创建跟进任务。
- 语义分析重试由后端语义分析流程负责。
- 跟进任务创建由后端使用来源通话、来源 handoff 或话后处理记录保证技术幂等。
- AI 分析重复完成、Webhook 重放或页面重复刷新都不能创建第二条相同来源的跟进任务。
- 不同通话对同一客户形成的业务疑似重复任务只提示，不在列表层自动合并。

## 11. 验证

### 11.1 前端自动化

- 正向、中性、负向、待分析和分析失败映射正确。
- Mock、无有效客户话术和无需跟进记录展示 `-`。
- 真实跟进任务状态覆盖“建议跟进”。
- 有任务但状态非法时展示“状态异常”。
- 两列每行最多各出现一个标签，不渲染全部语义标签。
- 客户意向和跟进状态筛选参数正确提交给后端。
- 点击意向标签打开对应通话详情。
- 点击真实跟进状态携带 `followUpId` 进入跟进任务详情。
- 列表不对每行发起语义分析或跟进任务请求。
- 存在非稳定状态时启用单飞轮询，稳定后停止，页面失焦时不堆积请求。

### 11.2 后端自动化

- 列表接口按分页批量聚合意向和跟进状态，没有 N+1 查询。
- 客户意向和跟进状态筛选作用于完整结果集。
- `followUpSuggested` 只来自结构化话后结果。
- 跟进任务状态优先级和异常数据返回规则正确。
- 同一来源重复触发时只存在一条跟进任务。
- bigint ID 始终以字符串返回。
- 租户隔离和跟进任务查看权限保持生效。

### 11.3 人工验收

至少准备以下记录：

1. 正向但无需跟进。
2. 正向且仅建议跟进。
3. 已创建待跟进任务。
4. 跟进中的任务。
5. 已完成任务。
6. 负向且明确拒绝后续联系。
7. 语义分析中和分析失败。
8. Mock、无人接听或无有效客户话术。

逐项确认列表标签、筛选、详情跳转和刷新后的状态一致。页面标签只能证明当前业务数据状态，不能替代真实回拨和通话完成证据。

## 12. 实施边界

本设计需要前后端协同：

- 后端补充统一话后结果和通话记录列表聚合字段。
- 前端增加两列、筛选、状态映射和详情跳转。
- 跟进任务管理页增加 `followUpId` 深链接定位。
