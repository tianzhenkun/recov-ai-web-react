# 坐席转人工可靠性与完整对话区设计

## 1. 背景与现场证据

2026-07-31 的真实 Linphone 转人工验收已证明以下链路真实可用：

- 正式外呼任务由 `sip` 拨号器执行并接通；
- 实时 ASR、LLM、TTS 和对话持久化正常；
- 转人工请求能够创建并出现在坐席待接池；
- 主录音、客户分轨、AI 分轨、离线 ASR、语义分析和通话摘要均能完成；
- 转人工无人接通后能够生成 `handoff_unanswered` 跟进任务。

同一次验收也暴露了四类需要修复的问题：

1. 坐席首次认领返回数据库事务异常：
   `Can't operate on closed transaction inside context manager`。
2. 第二次认领返回 200，但坐席浏览器未在连接窗口内完成
   `media-ready`，最终状态为
   `expired / handoff_unanswered / handoff_timeout`。
3. 后端切换执行器重启时，坐席页面暴露原始 504 错误。
4. 右侧上下文区域只展示最近 6 条对话，宽度和信息层级不足。

本设计以真实转人工成功为最高优先级，UI 优化不能替代认领和媒体链路修复。

## 2. 目标与成功标准

### 2.1 P0：首次认领原子成功

坐席对有效的 `requested` 转人工请求执行认领时：

- 首次请求返回 200；
- 转人工状态持久化为 `accepted`；
- 坐席状态持久化为 `claiming`；
- 两项状态必须属于同一个原子事务；
- 响应中的 LiveKit 凭证只能在事务提交成功后签发；
- 事务失败时不能出现一方已占用、另一方未认领的半完成状态；
- 同一幂等键重试不得产生重复认领或状态倒退。

### 2.2 P0：坐席媒体真实就绪

认领成功后，坐席浏览器必须按顺序完成：

1. 使用认领响应中的 LiveKit URL 和 Token 连接房间；
2. 创建并发布本地麦克风轨道；
3. 调用 `media-ready`；
4. 后端将转人工状态更新为 `connected`；
5. 后端将坐席状态更新为 `in_call`；
6. Linphone 客户与浏览器坐席能够双向听见声音。

任何一步失败都必须在坐席页面展示具体阶段，而不是只显示笼统的“接入失败”。

### 2.3 P1：网关错误可恢复

后端短暂重启或代理上游不可用时：

- 坐席页面框架继续显示；
- 不向业务用户展示原始 `502/503/504`；
- 显示“坐席服务暂不可用，正在重新连接”；
- GET 类状态读取每 3 秒重试一次，最多 5 次；
- 恢复后自动刷新坐席档案、在线状态和待接池；
- 重试耗尽后显示“重新连接”按钮；
- 认领、结束通话等状态变更操作不做无条件自动重放。

### 2.4 P1：完整会话可读

右侧上下文区域采用已确认的 B3 方案：

- 右栏目标宽度约 480px；
- 顶部常驻客户信息和交接摘要；
- 删除含义不准确的“待处理事项”；
- 展示该次转人工前全部 AI 与客户最终对话；
- AI 消息左对齐，客户消息右对齐；
- 两类消息使用不同浅色背景；
- 不展示逐条消息时间；
- 对话区最大高度 600px，内容超出后内部滚动；
- 初次加载完成后定位到最新消息；
- 小屏时右栏下移到主工作区下方，禁止产生页面横向滚动。

## 3. 范围

### 3.1 本轮包含

- 后端认领事务根因定位、回归测试和修复；
- 前端 LiveKit 接入阶段可观测性与 `media-ready` 修复；
- 坐席页面对 502/503/504 的友好恢复；
- 单条转人工完整上下文读取；
- B3 对话区布局；
- 后端、前端和浏览器验证；
- 修复完成后的第二轮真实 SIP 转人工验收。

### 3.2 本轮不包含

- 厂商 PSTN 或真实手机号码接入；
- 新的语义分析模型或摘要算法；
- 将“客户最后一句话”继续包装为待办事项；
- 对无关坐席管理页面进行重构；
- 自动发起第二轮真实呼叫。

## 4. 架构与数据流

### 4.1 待接池保持轻量

待接池接口继续返回每条请求的客户脱敏信息、场景、请求原因和交接摘要。
它不负责一次性返回队列中每个客户的完整会话。

这样可以避免队列中有多条请求时，首页响应体随所有历史对话成倍增长。

### 4.2 单条转人工上下文

新增坐席侧单条上下文读取能力。推荐契约：

```http
GET /ai-call/agent-console/handoffs/{handoff_id}/context
    ?console_session_id={console_session_id}
```

接口必须：

- 校验当前账号存在启用的坐席档案；
- 校验 `console_session_id` 属于当前坐席；
- 校验坐席有权处理该转人工请求对应场景；
- 仅返回当前租户的数据；
- 返回客户脱敏信息、交接摘要和完整对话；
- 对话只包含 `segment_status=final` 且
  `speaker_type in {ai, customer}` 的记录；
- 按原始发生顺序返回；
- 不返回转人工之后的人工坐席会话作为“转接前上下文”。

建议响应字段：

```json
{
  "handoff_id": "handoff_xxx",
  "call_id": "call_xxx",
  "masked_customer_name": "刘先生",
  "masked_contact": "199****1001",
  "scene_code": "intro_geo",
  "handoff_summary": "客户关注实施方式、效果验证和竞品对比",
  "dialogue": [
    {
      "id": "segment_xxx",
      "speaker_type": "ai",
      "text": "您好……",
      "occurred_at": "2026-07-31T07:04:51Z"
    }
  ]
}
```

`occurred_at` 保留用于排序、审计和问题排查，前端 B3 视图不展示。

### 4.3 前端加载流程

1. 页面加载坐席状态与轻量待接池；
2. 队首请求变化、坐席查看请求或认领成功时，读取该请求的单条上下文；
3. 右栏上下文请求期间展示骨架屏，不清空已经显示的稳定内容；
4. 请求成功后显示摘要和完整对话；
5. 请求失败时仅在右栏显示可重试错误，不影响待接池和当前工作区；
6. 新增对话到达时重新读取当前单条上下文，并保持滚动位置策略。

## 5. 认领事务设计

认领操作必须把以下两次条件更新放在同一个数据库事务内：

- `handoff: requested -> accepted`
- `agent: available -> claiming`

控制器不能在依赖提供的事务上下文已经关闭后继续发起数据库查询。
修复前必须用失败测试稳定复现本次
`InvalidRequestError`，再根据真实调用栈确定事务边界。

提交顺序要求：

1. 查询并校验请求、坐席、场景和会话所有权；
2. 条件更新转人工请求；
3. 条件更新坐席状态；
4. 在当前事务仍有效时准备不再依赖 ORM 懒加载的响应快照；
5. 提交事务；
6. 签发 LiveKit Token；
7. 发布状态事件。

提交后禁止继续使用已经关闭的事务上下文查询或懒加载 ORM 属性。
如果响应确实需要提交后的数据库状态，必须使用新的数据库会话读取。

如果第 2 或第 3 步失败，整个事务回滚并返回明确冲突码。

## 6. 媒体接入与可观测性

前端将接入流程拆成可识别阶段：

- `claim_succeeded`
- `livekit_connecting`
- `livekit_connected`
- `microphone_publishing`
- `microphone_published`
- `media_ready_reporting`
- `connected`

页面错误文案必须指出失败阶段，例如：

- “已认领，但无法连接通话房间”
- “已连接房间，但麦克风发布失败”
- “麦克风已就绪，但坐席状态确认失败”

浏览器仅在完成房间连接和麦克风发布后调用 `media-ready`。
后端收到 `media-ready` 后必须验证坐席参与者及麦克风轨道真实存在，再进入
`connected / in_call`。

认领连接窗口内的状态不能静默回退。回退或超时必须同时留下：

- 转人工结束原因；
- 坐席释放原因；
- 前端可见错误；
- 可用于复测的阶段信息。

## 7. 504 恢复策略

### 7.1 可自动重试

- `bootstrap`
- 待接池查询
- 单条上下文查询
- 其他只读状态查询

仅对网络错误和 `502/503/504` 执行每 3 秒一次、最多 5 次的有界重试。

### 7.2 不自动重放

- 上线、暂停、下线；
- 认领；
- `media-ready`；
- 结束通话；
- 提交话后结果。

这些操作必须依赖既有幂等键由用户显式重试，避免前端在未知响应状态下重复改变业务状态。

## 8. UI 设计

右侧卡片结构：

1. 客户名称、脱敏联系方式、业务场景；
2. 常驻交接摘要卡；
3. “完整会话”标题和消息总数；
4. 最大高度 600px 的滚动会话区；
5. AI 左侧浅蓝/白色气泡；
6. 客户右侧浅紫色气泡。

不展示：

- “待处理事项”；
- 逐条时间；
- 仅用于排查的内部 ID；
- 原始网关错误码。

## 9. 状态与异常

### 9.1 正常状态

```text
requested
  -> accepted / agent claiming
  -> connected / agent in_call
  -> completed / agent wrap_up_quick
```

### 9.2 异常状态

- 认领冲突：保留原业务状态，返回明确冲突码；
- LiveKit 连接失败：释放坐席占用并记录失败阶段；
- 麦克风发布失败：不调用 `media-ready`，允许用户修复设备后重试；
- `media-ready` 失败：保留幂等键，展示可重试操作；
- 客户提前挂断：进入话后处理，不伪装为人工接通；
- 接入超时：创建人工未接回访，并记录具体超时阶段；
- 上游 504：保持页面框架，执行有界只读重试。

## 10. 测试与验收

### 10.1 后端

- 使用真实 SQLite 事务上下文复现首次认领异常；
- 首次认领成功后的状态原子性测试；
- 同幂等键重复认领测试；
- 坐席冲突、场景不匹配、请求过期测试；
- `media-ready` 参与者和麦克风验证测试；
- 单条上下文权限、排序、说话人过滤和完整性测试。

### 10.2 前端

- 504 映射为友好文案；
- 3 秒间隔、最多 5 次的有界重试；
- 状态变更操作不被自动重放；
- B3 摘要常驻；
- 不展示“待处理事项”和时间；
- AI 左、客户右；
- 全部对话渲染；
- 最大高度和内部滚动；
- 接入阶段错误文案测试。

### 10.3 浏览器

- 页面无横向滚动；
- 右栏在常见桌面宽度下可读；
- 窄屏时右栏下移；
- 后端短暂停止后页面显示重连状态并能恢复；
- 使用浏览器坐席完成认领、LiveKit 连接、麦克风发布和
  `media-ready`。

### 10.4 第二轮真实 SIP 验收

自动化和浏览器验证完成后，必须再次获得用户明确的“确认拨打”，才能：

1. 创建或确认新的正式任务；
2. 启用 SIP 执行器；
3. Linphone 接通客户侧；
4. 触发转人工；
5. 坐席首次认领成功；
6. 达到 `connected / in_call`；
7. 验证双方双向音频；
8. 正常结束并核验录音、离线 ASR、语义分析、摘要和终态；
9. 关闭执行器。
